On how to send packets:

    When your driver starts (DriverEntry), or when your filter attaches to a miniport (FilterAttach), allocate a NET_BUFFER_LIST (NBL) pool with NdisAllocateNetBufferListPool. For typical usage, you'll want to get one NET_BUFFER (NB) automatically with each NBL, so set fAllocateNetBuffer=TRUE. If you want NDIS to allocate the data payload buffers for you, also give a non-zero DataSize. If you already have the packet payload in some other buffer, you can transmit faster by pointing the NB at the existing MDL, but this is also more complex to code up.
    To send a packet, allocate a new NBL from NdisAllocateNetBufferAndNetBufferList. Put your FilterModuleHandle into NBL->SourceHandle. Assign NB->DataLength and copy in the data. Call NdisFSendNetBufferLists on your new NBL. Do not touch the NBL until it's returned back to you.
    Eventually, NDIS will return the NBL back to you via FilterSendNetBufferListsComplete. Note that all NBLs come through there in one jumbled linked list -- both your own NBLs, as well as any NBLs you just passed through from above. So you have to slice the linked list based on NBL->SourceHandle: if the SourceHandle is yours, take the NBL out of the stream and free it via NdisFreeNetBufferList. Otherwise, if the NBL is not yours, continue propagating it along by calling NdisFSendNetBufferListsComplete.
    Do not allow FilterPause to complete until all the NBLs you originated have been returned to you. You can do this any way you want, but the usual approach is to add some refcounting to the send and sendcomplete paths. You are not required to worry about any NBLs that you didn't create.

When you're creating NBLs, you can use !ndiskd.nbl to double-check your work. It can detect a variety of errors. There's a likely problem with the NBL if ndiskd reports any field in red text.

On Oid requests :
NDIS itself calls the FilterOidRequestComplete when NDIS_STATUS_PENDING is returned. However, on the MSDN sample filter driver,
OID requests are first cloned, then passed down (NdisFOidRequest). The FilterOidRequest function assignes the status to the Original Oid Request and then calls NdisFOidRequestComplete. If a cloned Oid Request returns NDIS_STATUS_PENDING, the FilterOidRequest callback will be auto called by NDIS to assign the status to the original Oid Request and call NdisFOidRequestComplete
However, since OID Requests are cloned and since NDIS doesn't call FilterOidRequest if the status isn't pending, the filter driver calls the FilterOidRequest manually to complete the original OID request.

On how to handle kernel memory buffer and user mode reading requests:
we have three buffers:
One read only
One write only
One pending
A clock ticks and assign which is what :	[0,1,2] = 0 read only, 1 write only, 2 pending
						[1,0,2] = 2 read only, 1 write only, 0 pending
when writing an NBL into a buffer: the driver checks which buffer is write only and copies there, it indicates that the buffer write only is busy, and if the clocks ticks again, it will check if the buffer is being used.
if the buffer is being used, the buffer will remain write only, and the read only buffer will switch to the pending buffer instead.
If both buffers are busy, no change will be made
if one buffer is full for writing, the pending buffer is set to write only and used.

1/allocate pool from non paged memory (say 16MB)
2/split the pool into many buffers (say 32 sub buffers)
3/map large buffer to user space.
4/send 20 IOcontrols, each containing an offset to the large buffer representing a segment of the buffer
5/upon receiving (or transmitting) a packet, the FilterReceiveNetBufferList (or FilterSendNetBufferList) retrieves an IO control from the queue, copies the packet to the related segment, completes the IO control code (effectively removing it from the queue and making sure the memory described by it safe from being overwritten)
if the queue is empty, return the ownership of the packet without blocking it. alternatively, it could copy up to ten packets to the same segment and then issue the completion to usermode, to process packets in batch. (the overall idea is that of the inverted call described on OSR forums)
INSTEAD of using fixed size batches, fill the buffer completely before completing the IO request. as long as there is free space in the buffer, copy the net buffer list inside the buffer. If there is not enough room in it, then complete the request, retrieve a new request and copy the packet inside the new segment. this comes from the idea that if there is no more pending request, I might as well just hang onto the last IO request until the buffer is filled or there is a new pending IO request to be retrieved in one of the queue. this is an improvement from the fixed size packet batch? it avoids some packet loss.
so yeah, the intial Idea was to keep fixed size batches, kept losing some packets, so instead tried to hold onto the last pending io control code until another one was available and try to copy the packet in its described buffer segment and then start dropping packets if the LAST segment was full.
Instead, I might as well just stop using fixed size and start holding onto all of the IO control codes as long as the segment isn't full.
6/whenever user space app receives the completion routine, it issues a read request to the segment. this segment would be "owned" by the user space app in that it would be impossible to be used by the packet copying routine in the driver (the segment has been retrieved from the Queue and completed)
7/ when the user app is done reading, it issues the IO control code describing the segment back to the driver, returning ownership of the segment to the driver, so that it can be reused.
The goal is to run the NBL copying synchronously, and then let the user app read it asynchronously. the Inverted call is said to be rather quick, and it avoids allocating memory per packet and doing the reading synchronously.
The goal is also to enforce strict ownership rules in order for the driver not read and write a memory block at the same time and prevent a bug check. it should be manual locking free (wdf queue locking is done by the framework)
every routine called would be able to run at IRQL <= dispatch level (the driver is based on the MSDN filter driver sample, and the red teams tactics WFP callout driver).
